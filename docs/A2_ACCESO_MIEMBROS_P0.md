# A2 P0 — motivo y rastro de cambios de acceso del centro

**Canary publicado el 28/09/2026:** desde `c178f5a115f18c3c6296ae1222168d555697b712`, después de CI `SUCCESS` en Node 22 (run `36371952037`), sólo en `pie-diabetico-canary-2026`. Function `api` hash `ab4564456713118f62f13538dd331f7820fd98be`; Hosting versión `1a27fe2be7f524f8`, release `1790607426012000`. La página y el JS remoto coinciden con la compilación canary; salud 200 y sesión anónima 401. No se hizo un cambio remoto autenticado de membresía, por lo que ese cotejo operativo sigue pendiente. Antes de administrar accesos hay que recargar sesiones abiertas antes de esta publicación. La publicación no autoriza pacientes reales ni producción.

**Candidata local:** rama `codex/a2-admin-member-audit`, base `7bccd42061a47ee3278695a6bdddd2acaa02efd3`. Este alcance cubre sólo invitación, desactivación/reactivación y perfiles de membresías mediante la API del centro. No crea, deshabilita ni borra cuentas de Firebase Auth.

La interfaz exige un motivo administrativo de 10 a 200 caracteres y advierte que no se incluyan datos de pacientes. La API exige ese motivo y un UUID de operación; rechaza formatos habituales de correo, RUT, número largo y enlace. Este filtro reduce errores evidentes, pero no puede demostrar que todo texto libre esté libre de datos clínicos. El `center_admin` activo conserva la decisión local sin aprobación institucional por cambio.

La API revalida en la transacción el centro y el UID/rol/estado del administrador. El cambio y `centers/{centerId}/auditLogs/{operationId}` se confirman juntos. El evento guarda actor verificado, centro, acción, membresía de destino, perfiles/estado anteriores y nuevos, motivo, `requestId`, `operationId`, resultado `succeeded` y estado HTTP. El hash de la petición sirve para aceptar sólo un reintento idéntico del mismo actor; si el acceso cambió después, responde 409 y pide actualizar el equipo. La interfaz conserva el UUID al reintentar la misma acción fallida. Los rechazos y fallos de la ruta emiten un evento técnico `member_access_change` con resultado `failed`, estado, actor y centro sólo cuando ya se conocen; no copian el motivo ni la petición. Un fallo al escribir la bitácora aborta la transacción y no cambia la membresía.

**Verificación local sintética:** `npm run validate` pasó (27 pruebas unitarias, TypeScript, build y sintaxis). `npm run test:emulators` pasó (61 comprobaciones base, 41 eventos de auditoría en la ejecución), incluyendo permiso denegado, motivo ausente, alta/cambio con antes/después y correlación, repetición idéntica y colisión del identificador de auditoría sin crear la membresía. No hubo lectura ni escritura remota de Firebase ni despliegue.

**Límites y siguiente condición:** el conflicto de evento en emulador cubre la obstrucción del registro, no una caída real de Firestore o Cloud Logging. El resultado fallido queda en el log técnico, cuya retención, protección y acceso requieren R2. Las vías directas Auth/Firestore/Storage/IAM, el resto de operaciones administrativas y el cotejo remoto A3 siguen pendientes. Este P0 no cierra A2 integral, R0 ni un GO clínico/productivo.
