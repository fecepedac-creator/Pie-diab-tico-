## Decisión actual

**No existe un canary Firebase utilizable todavía.** `simulador-clinico` es el destino único: alias `canary`/`staging` de `.firebaserc`, proyecto Firebase activo y base Firestore propia. Blaze y la consulta de Functions están habilitados, pero Hosting no tiene release activo y no se han verificado Storage, Auth, permisos de despliegue, datos existentes ni restauración. `simulador-clinico-2` no es alternativa inmediata: Cloud Functions y Firestore API estaban deshabilitadas en el corte previo, y su Hosting sólo servía una versión estática anterior.

Son proyectos y recursos separados del principal `policlinico-de-pie-diabetico` (número `953735305510`). Esto confirma separación de identidad de proyecto, **no** que estén vacíos ni libres de datos reales. La observación del 13/09 sobre health/API coincide con este corte, pero los documentos de esa fecha son históricos y no sustituyen estas consultas.

**Verificación local del procedimiento:** `check:canary:health` y `verify:canary` consultaron `simulador-clinico` y fallaron por el 404 esperado, sin consultar el dominio principal. `build:canary` rechazó variables faltantes; con valores ficticios de prueba y la identidad canary construyó el bundle. En ese bundle apareció `simulador-clinico` y no apareció el ID del proyecto principal. `git diff --check` pasó. Esto valida los guardas locales, no una publicación remota.

## Preparación para una tarea posterior de canary

1. Resolver las revisiones técnicas de la candidata y el cierre R0 antes de autorizar publicación. Blaze quedó activo y Functions es consultable, pero aún no existe la Function. Confirmar en consola el bucket de Storage, Auth, cuotas, región `southamerica-west1`, permisos y las APIs requeridas por Functions de segunda generación. Repetir `firebase firestore:databases:list --project simulador-clinico`; exigir resultados legibles, sin `SERVICE_DISABLED`. Confirmar que no hay datos clínicos reales en el destino antes de crear usuarios o cargar datos sintéticos.
2. Congelar **un commit exacto** de la candidata aprobada. Desde un checkout limpio de ese commit, registrar SHA y estado Git. Ejecutar `npm run validate` y `npm run test:emulators` con `demo-pie-diabetico`. Estas pruebas son locales; no prueban servicios remotos.
3. Obtener la configuración de la app web correcta con `firebase apps:sdkconfig WEB 1:328428681603:web:f0dab1f3ed8283be9b1eb6 --project simulador-clinico`. Preparar `.env.canary` local (ignorado por Git) con `VITE_API_URL=/api` y todos los `VITE_FIREBASE_*` de esa app; usar `VITE_FIREBASE_AUTH_DOMAIN=simulador-clinico.web.app` y confirmar que ese dominio está autorizado en Firebase Auth. El bucket debe pertenecer a `simulador-clinico`. Ejecutar `npm run build:canary`; el guard rechaza configuración faltante, otra identidad y referencias al proyecto principal. Inspeccionar el bundle construido y el plan de despliegue contra el SHA congelado.
4. Antes del primer despliegue, registrar canales/release y configuración remota (`firebase hosting:channel:list --site simulador-clinico --project simulador-clinico --json`, `firebase functions:list --project simulador-clinico`, reglas Firestore/Storage y estado de Auth/Storage). Establecer cuentas y centros **ficticios**; prohibir importaciones, enlaces, cuentas o identificadores de pacientes reales. La API usa Admin SDK del proyecto donde se ejecuta; el frontend debe apuntar al mismo proyecto. Revisar además que las reglas incluidas en el release corresponden a la candidata.
5. Con aprobación de la tarea de publicación, desplegar desde el checkout exacto y con proyecto explícito. Publicar y comprobar cada capa por separado: `firebase deploy --only functions:api --project simulador-clinico`, después reglas necesarias (`firebase deploy --only firestore:rules,storage --project simulador-clinico`, sólo tras revisar Storage), y finalmente `firebase deploy --only hosting --project simulador-clinico`. Registrar ID de release de Hosting, versión de Function, revisión de reglas, SHA, operador y hora. Un 200 de Hosting por sí solo no prueba que Functions esté desplegada.
6. Comprobar `npm run check:canary:health` y `npm run verify:canary` (ambos apuntan al canary por defecto). Exigir `/api/health` HTTP 200 JSON con `status:"ok"`, `/api/session` sin token HTTP 401, portada con bundle JS y ninguna referencia al proyecto principal en el bundle. Luego ejecutar los flujos mínimos de sesión, permisos por rol/centro, alta y lectura **sintéticas**, foto sintética y auditoría; verificar que los registros aparecen sólo en `simulador-clinico`. No usar el dominio principal para declarar canary aprobado.

## Observación y reversión

- Observar 24–48 horas con responsables y horario registrados: disponibilidad/latencia de `/api/health`, errores de Functions, denegaciones de permisos esperadas frente a inesperadas, eventos de auditoría, uso de Firestore/Storage, cuotas y costo. Ejecutar al inicio y cierre una comprobación de aislamiento de datos y una prueba de recuperación **del destino canary**, con datos ficticios. Registrar incidentes y sus horas en este documento cuando se ejecute la tarea posterior.
- **Revertir o detener la prueba** ante health distinto de JSON 200 `ok`, sesión anónima distinta de 401, cruce de centro/proyecto, datos reales detectados, pérdida de auditoría, error persistente de guardado/lectura, o impacto/costo fuera del límite aprobado. Detener acceso de testers, preservar logs y versiones y no promover a piloto.
- Si existía una versión anterior **verificada**, restaurar Hosting desde su canal/version registrada y volver a desplegar la versión anterior exacta de Functions y reglas; confirmar cada capa y volver a ejecutar health, sesión, aislamiento y lectura sintética. No asumir que revertir Hosting revierte Functions, reglas o datos. Para el **primer release** de `simulador-clinico`, no hay versión anterior observada: mantener el sitio fuera de circulación y decidir con el responsable la deshabilitación de Hosting/Function, conservando evidencia. Los documentos sintéticos creados requieren un plan explícito de limpieza; el rollback de código no los borra.

**Salida hacia la siguiente tarea:** candidata y R0 aprobados; servicios requeridos habilitados y verificables; destino sin datos reales confirmado; configuración web canary y bucket correctos; responsable/ventana/costo definidos. Sólo entonces ejecutar el despliegue y registrar pruebas y observación. Hasta ese punto: **NO-GO para despliegue y uso clínico**.
